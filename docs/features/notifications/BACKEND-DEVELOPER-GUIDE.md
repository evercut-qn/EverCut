## 3. REST API Routes

All endpoints require an authenticated `Authorization: Bearer <token>` header.

| Method | Endpoint | Access Control | Description |
| :--- | :--- | :--- | :--- |
| `POST` | `/api/v1/notifications/tokens` | Authenticated | Registers or updates a device token. |
| `DELETE` | `/api/v1/notifications/tokens/:token` | Authenticated | Revokes a caller-owned device token (via path parameter). |
| `GET` | `/api/v1/notifications/inbox` | Customer / Barber | Lists personal inbox notifications. |
| `GET` | `/api/v1/notifications/inbox/unread-count` | Customer / Barber | Gets the unread badge count for the caller. |
| `GET` | `/api/v1/notifications/inbox/:id` | Owner | Gets details of a personal inbox notification. |
| `PATCH` | `/api/v1/notifications/inbox/:id` | Owner | Marks a specific inbox notification as read. |
| `PATCH` | `/api/v1/notifications/inbox` | Customer / Barber | Marks all personal inbox notifications as read. |
| `GET` | `/api/v1/notifications/broadcasts` | `ADMIN` Role | Lists bulk broadcasts. |
| `POST` | `/api/v1/notifications/broadcasts` | `ADMIN` Role | Creates a bulk broadcast notification (async dispatch). |
| `GET` | `/api/v1/notifications/broadcasts/:id` | `ADMIN` Role | Gets details and delivery metrics of a broadcast. |
| `GET` | `/api/v1/notifications/broadcasts/:id/recipients` | `ADMIN` Role | Lists resolved recipients of a broadcast with per-token delivery detail. |
| `GET` | `/api/v1/notifications/broadcasts/:id/inbox-items` | `ADMIN` Role | Lists individual inbox feed items generated by a broadcast. |
| `GET` | `/api/v1/notifications/broadcasts/:id/audits` | `ADMIN` Role | Lists operational audit logs of a broadcast. |

### 3.1 Broadcast Detail Response Contract

To avoid domain confusion, the broadcast response contract strictly separates **persisted device-level operational statistics** (`metrics`) and **derived user-level campaign outcomes** (`reporting`). It also provides a user-friendly `displayStatus` mapping.

Example response payload for `GET /api/v1/notifications/broadcasts/:id`:

```json
{
  "success": true,
  "data": {
    "id": "60a7c0000000000000000001",
    "title": "Weekend Promotion",
    "body": "Book now and get 10% off!",
    "type": "hybrid",
    "category": "admin_broadcast",
    "status": "sent",
    "displayStatus": "Completed",
    "audience": {
      "mode": "customers"
    },
    "data": {},
    "metrics": {
      "recipientCount": 150,
      "tokenCount": 200,
      "successCount": 185,
      "failureCount": 10,
      "invalidTokenCount": 5,
      "skippedCount": 5
    },
    "reporting": {
      "deliveredUsers": 135,
      "failedUsers": 10,
      "offlineUsers": 5
    },
    "sentAt": "2026-06-10T12:00:00.000Z",
    "completedAt": "2026-06-10T12:01:00.000Z",
    "createdAt": "2026-06-10T11:55:00.000Z",
    "updatedAt": "2026-06-10T12:01:00.000Z"
  },
  "message": "Broadcast details fetched"
}
```

#### Naming and Structure Specifications
1. **`status` & `displayStatus`**:
   - `status`: Raw database status (`sending`, `sent`, `failed`).
   - `displayStatus`: Formatted status for user-facing UI dashboards (`Processing`, `Completed`, `System Error`).
2. **`metrics` (Persisted operational data)**:
   - Tracks lower-level operational and device-level counts: `recipientCount` (number of targeted users), `tokenCount` (number of resolved FCM tokens), `successCount` (multicast success replies), `failureCount` (multicast errors), `invalidTokenCount` (tokens reported unregistered/invalid by FCM), and `skippedCount` (recipients skipped due to no registered tokens).
3. **`reporting` (Derived user-level data)**:
   - Computed at read-time on detail requests using a MongoDB aggregation pipeline on `NotificationRecipient`.
   - `deliveredUsers`: Count of users who successfully received the notification on at least one device (`successCount > 0` and `skippedReason == null`).
   - `failedUsers`: Count of users where all delivery attempts failed (`successCount == 0` and `tokenCount > 0`).
   - `offlineUsers`: Count of users who had no active registered device tokens (`skippedReason != null`).

## 5. Adding a New Domain Event

To add a new notification event (e.g., a new booking state or business alert):

1. **Add Event Enum**: In `server/src/utils/constants.js`, add the new key/value to `NOTIFICATION_EVENT`:
   ```javascript
   export const NOTIFICATION_EVENT = Object.freeze({
       // ...
       NEW_AWESOME_EVENT: 'new.awesome_event',
   });
   ```
2. **Add Event Trigger Service**: In `server/src/services/notifications/notification-events.service.js`, implement a trigger function:
   ```javascript
   export const notifyNewAwesomeEvent = async ({ userId, dataPayload }) => safeNotify(
       async () => {
           return notificationService.notifyUser({
               recipientUserId: userId,
               type: NOTIFICATION_TYPE.HYBRID,
               eventType: NOTIFICATION_EVENT.NEW_AWESOME_EVENT,
               title: 'Awesome Update',
               body: 'Something awesome occurred!',
               data: dataPayload,
               entityType: 'awesome',
               entityId: dataPayload.id,
           });
       },
       { eventType: NOTIFICATION_EVENT.NEW_AWESOME_EVENT, userId }
   );
   ```
3. **Trigger Event**: Import and call `notifyNewAwesomeEvent` from your business logic service.
4. **Validation rules**: Data payloads passed to FCM are validated; any key starting with `google.`, `gcm.`, or `gcm.notification.` will be rejected to prevent FCM reserved namespaces issues.

## 6. Reliability and Background Jobs

The platform includes built-in mechanisms for reliability and background maintenance.

### 6.1 FCM Retry with Exponential Backoff
Transient delivery failures when communicating with the FCM server (e.g., rate limits or network issues) are retried automatically:
- **Max Retries**: 2 additional attempts.
- **Backoff Algorithm**: Exponential backoff with a base of 1000ms ($2^{\text{attempt}} \times 1000$ ms) plus a random jitter up to 100ms.
- **Retryable Errors**: `messaging/internal-error`, `messaging/server-unavailable`.
- **Permanent Errors**: Stale tokens (`messaging/invalid-registration`, `messaging/registration-token-not-registered`), bad requests, or configuration errors are NOT retried.

### 6.2 Stale Token Cleanup
A background cron job runs weekly to clean up inactive tokens:
- **Centralized Configuration**: The staleness threshold (90 days) and weekly schedule (`0 3 * * 0`, Sunday at 03:00 in Asia/Kolkata timezone) are defined under the `notification` block in `server/src/config/index.js` as frozen constants.
- **Action**: Stale tokens are deactivated/deleted in the database to maintain optimal storage and dispatch speed.

### 6.3 Startup Recovery Scan
On server startup, a recovery scan runs to check for broadcasts that were left in the transient `sending` status due to a server crash or sudden restart:
- **Action**: Any broadcast stuck in `sending` state for more than 5 minutes is updated to `failed`.
- **Context Preservation**: A detailed description is logged into `failureReason` noting how many recipients were processed vs how many were remaining at the time of recovery.
